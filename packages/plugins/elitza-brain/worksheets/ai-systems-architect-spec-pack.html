This is the document I write before I quote a system. Not a slide deck. Not a call summary. A spec with fixed boundaries, named approval gates, a data path your team can review, and a handover plan. You get the template, worked examples, and the reading that turns it into a fixed price.

Before you start

A spec fails when it describes a vision instead of a boundary. The test is simple. A developer who was not in the room should be able to read it and know what is in, what is out, what needs a human, and what happens when the model is wrong. If a line cannot pass that test, cut it.

The price comes last. Scope, gates and data path are the inputs. The number is the output.

Ground rules: write the scope statement first, the gates second, the data path third, the estimate last. Every decision above the estimate changes the estimate. Reverse the order and you will spend the build renegotiating what the build is.

Section 1 · Scope: what ships now, what waits

Scope is a list of boundaries, not a list of features. What ships now is the smallest system that does one money-path job end to end. What waits is everything else, written down so nobody has to renegotiate it later. A boundary that lives only in a conversation is not a boundary.

Why the out-of-scope list exists: the expensive part of a build is not the code. It is the mid-project redefinition. A named wait list turns "can we also..." into a scheduled item instead of a surprise. In the D'Alessio Law Group intake work, the four stages that shipped were capture, qualification via Claude API, attorney routing and dual-CRM sync to Lawmatics and MyCase. Everything else sat outside the line.

Boundary checks before you lock scope

One outcome sentence: if you cannot write it in one sentence, the system is still two systems.
Named waits: every adjacent feature the team already wants appears on the wait list with a trigger.
Read and write lists: every integration is marked read-only or read-write. "Touches HubSpot" is not a spec.
Definition of done is a test: a number of cases, a field that must be set, a log line that must exist. Not "works well".
No owner, no scope: if nobody on the client side can approve a gate, the feature does not ship in this build.
Common scope failure: listing capabilities instead of boundaries. "The agent handles lead qualification" is a capability. "The agent classifies each inbound lead into one of six labels, writes sales_priority or nurture, and never sends an email without approval" is a boundary. Write boundaries.

Section 2 · Approval gates and permission boundaries

Every write action in the system gets one of three gate classes. Auto-execute runs without a human. Human-approve waits for a named person. Blocked never runs inside this build. The gate class is a spec decision, not an implementation detail. Decide it in the document.

Permission boundary checks

Every write has a gate class on the spec, before any connector is built.
Every gate has a named approver role, not a person's name alone. People change roles. Roles stay.
Timeout behaviour is written: hold and alert, escalate, or auto-deny. Silence is not a behaviour.
Client-facing sends are L2 or L3: the agent may draft, the system may not publish without a human.
Tokens are scoped and owned: each key has an expiry review date and a person who can rotate it.
Common gate failure: approving the wrong thing. A human is asked to click "OK" on a raw model dump. The approver needs the rule decision, the fields that matter and the raw output beside each other. If the review screen cannot show that, the gate is decoration.

Data path review checklist

Every copy is on the diagram, including caches, model logs and Slack messages that quote a record.
Consent is captured at the source and travels with the event, not re-derived later.
Sensitive fields are classified before the first connector is built.
Retention numbers are real: a duration the client can live with and a deletion method that runs without a human.
The log store is on the path: if a write can happen without a log line, the path is incomplete.
Client review move: put the diagram on one page and walk it left to right in the demo. The questions that come up are the spec. Write the answers into Table 3A the same day.

Section 4 · Milestones, weekly demos and handover

Two to four week builds do not need a Gantt chart. They need a weekly proof. Each week ends with something running against real data, on a staging path, with the client watching. The demo is the schedule.

WEEK 1Skeleton and the happy path

What ships: receiver, schema validation, identity layer, one write path, event log.

What I demo: one test event end to end, raw payload on screen, log line that names every step.

Pass condition: required fields present, idempotency key stored, owner resolves to an active user.

Common failure: building the model step before the write path can record what the model decided.

WEEK 2Gates, permissions and the failure path

What ships: gate wiring, scoped tokens, dead-letter handling, first alert route.

What I demo: one approved action, one rejected action, one forced failure that lands in a visible queue.

Pass condition: every write has a gate class live, every failure carries its payload and correlation ID.

Common failure: ignore-error flags on modules, alerts routed to a channel nobody watches.

WEEK 3Edge cases and the real data run

What ships: retry behaviour, duplicate handling, the wait-list items explicitly deferred.

What I demo: the same flow on ten real records, including one that should be blocked.

Pass condition: definition of done from Table 1A met on a test batch the client chose.

Common failure: testing only the clean sample. The break hides in the messy record.

WEEK 4Handover and ownership transfer

What ships: runbook, monitoring checklist, token owners, retention schedule, support boundary.

What I demo: the system forced into an error path, the alert firing, the runbook page that says what to do.

Pass condition: the client team can explain the path and clear a gate without me in the room.

Common failure: handover as a folder dump. Ownership transfer is a checklist with names on it.

Handover checklist

Runbook: what the system does, what each alert means, what to do first.
Token register: every key, its scope, its owner, its rotation date.
Gate roster: every human-approve gate and the role that clears it.
Retention schedule: what is stored, for how long, how it is deleted.
Alert routes: where failures go, who is on call for the first two weeks.
Support boundary: what I fix after handover, what becomes a new engagement.
Access revocation: setup credentials removed or rotated, confirmed in writing.
Handover test: the client team runs one weekly demo themselves. If they can trigger it, read the log and clear a gate without me, the system is theirs. If they cannot, handover is not done and the week is not closed.

Failure modes I always register

Model output drift: classification leaves the closed list, confidence drops, phrasing changes after a provider update. Mitigation: validate against a closed set, store raw output, route rejects to a human queue.
API auth expiry: token rotated or scope narrowed while the chain keeps calling. Mitigation: owner on every key, expiry review, 401 and 403 alert rules.
Rate limits and burst imports: a CSV import trips the limit and half the writes vanish. Mitigation: queue, backoff, batch caps, partial-failure report.
Schema drift at the source: a form field is renamed and the payload shape moves. Mitigation: schema validation at the receiver, reject unknown shapes, alert on mismatch.
Duplicate and replay: a webhook retries and the second run creates a second record. Mitigation: idempotency key, search-before-create, raw payload archive.
Vendor outage: the CRM or the model provider is down during a batch. Mitigation: dead-letter queue, replay procedure in the runbook, no silent drop.

Assumptions that hold the price

  • Staging access to every write target before week one ends.
  • One named approver role per human-approve gate, reachable during the build.
  • Scope changes after sign-off move to the wait list or reopen the estimate. They do not enter the fixed number quietly.
  • Third-party limits (API plan, seat count, webhook availability) are the client's to provide. I design around the plan you have.
  • Definition of done is the test written in Table 1A. Not a general sense of finished.

How I read the quote back

I walk the spec in order and price the rows. Scope sets the work packages. Gates set the review surface. The data path sets the integration count and the retention work. The risk register sets the contingency, which is a named line, not padding. If the total needs to come down, we cut scope lines together. I do not shrink the estimate and leave the scope standing.

Section 6 · FAQ

Who is this for?

Operators and founders who are about to commission an AI system, and architects who need a repeatable spec format. If you write the scope yourself, you can hold a fixed price conversation on your terms.

Is this a proposal template?

No. A proposal sells the idea. A spec fixes the boundary, the gates, the data path and the handover. I write this before I quote, and I send the quote only after the spec holds.

What size of build does it cover?

Two to four week systems. Webhook intake, CRM writes, classification with a model API, approval queues, document routing, onboarding agents. Larger programmes can use the same sections as their discovery artefact.

Do I need technical staff to use it?

You need someone who can name the systems and the fields. The worksheets are written for that person. The JSON blocks are there so a developer can lift the contracts without rewriting them.

What if the scope changes mid-build?

It becomes a wait-list item or it reopens the estimate. That is the whole point of the fixed price. Silent scope growth is what the document is built to prevent.

Can you build from the spec I write with this?

Yes. Send the completed spec and it becomes the working boundary for an implementation engagement. You can also hand it to your own team. The format does not depend on me.

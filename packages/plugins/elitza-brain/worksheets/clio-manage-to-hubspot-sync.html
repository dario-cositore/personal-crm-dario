Two systems, one buyer, zero tolerance for duplicates. This is the sync map I build when a firm runs intake in Clio Manage and business development in HubSpot. Field by field, in the order the data actually moves. Work the sections in order. The order is the sync.

Before you start

Native integrations between Clio Manage and HubSpot sync the easy fields and stop. Names and emails move. Custom fields, related contacts and multi-select arrays do not. So someone on the intake team copy-pastes matter updates into the CRM, and every keystroke is a chance to record the wrong thing.

I built this map after watching a HubSpot instance across three offices turn into a data graveyard. Not because HubSpot was wrong: because both systems believed they owned the contact. Bidirectional sync without a source-of-truth rule and a dedupe gate produces duplicates on both sides. The map below decides who owns what before a single record moves.

Ground rules: pick the source of truth before you write a mapping. Dedupe before create, on email and phone, on both sides. Leave billing, time entries and privileged notes in Clio: they do not belong in a CRM, and syncing them creates compliance exposure. Work the sections in order.

Clio custom fields travel as an array

Clio expects custom fields as an array of objects, not a flat property bag. In Make.com an Iterator formats the HubSpot properties and an Array Aggregator rebuilds the exact payload Clio accepts. Miss the aggregator and the write fails on shape, not on content.

Section 3 · Dedupe before create, on email and phone

Bidirectional sync creates duplicates the moment one side creates before it searches. Every new contact in either system queries the other first. Email first, phone second, company domain third. Matches update. Non-matches create. There is no third option.

STEP 1Receive and store the raw event

What I check: the webhook payload lands in storage with event_id and idempotency_key before any lookup.

Evidence to collect: the archived payload and the provider delivery log entry.

Pass condition: the event is replayable even if the sync fails at step 4.

Common failure: parse first, store never. A vendor payload change then destroys the evidence.

STEP 2Search the other system

What I check: email, phone and company domain queries run against the counterpart before any create.

Evidence to collect: search request, response count, matched record ids.

Pass condition: zero matches creates, one match updates, multiple matches go to review.

Common failure: a loose search returns three records and the chain updates the first one without validating.

STEP 3Resolve the match tier

What I check: email exact, phone E.164 exact, then domain. Each tier carries its confidence.

Evidence to collect: which key matched, the confidence, the matched record id.

Pass condition: the match tier is written to the sync log so a human can audit the decision.

Common failure: name-only matching merges two different people who share a surname.

STEP 4Write with an idempotency key

What I check: create or update carries the idempotency_key so a replay never doubles the record.

Evidence to collect: the key string, the write response, the returned object ids.

Pass condition: replaying the same event produces zero new records.

Common failure: the provider retries, the chain creates again, and the firm now has two contacts for one buyer.

The one rule that prevents most sync damage: dedupe before create, on email and phone, on both sides. Everything else in this blueprint is detail. Skip this and the firm ends up managing duplicates instead of matters.

Section 4 · Retries, rate limits and the replay log

APIs fail in boring ways: rate limits, expired tokens, timeouts, a 500 from a vendor deploy. The sync is only as good as what it does in those minutes. Clio Manage enforces a rate limit of 100 requests per minute. A bulk import against that ceiling without a queue produces 429s across the run and a partial state nobody can describe.

Replay instructions

Read the failure row first: direction, error class, attempt count. A 429 is a queue problem. A 400 is a mapping problem.
Fix the cause before replaying: token, mapping, enum, or rate limiter. Replaying into the same fault multiplies the log.
Replay with the original idempotency key: same key, safe write. A fresh key can create a duplicate.
Watch the dedupe gate on replay: the search-before-create path must run again, not skip to create.
Record the outcome in the log: replayed, rejected, or merged. An unmarked replay is a future mystery.
Cap the attempts: after the ceiling the event moves to the dead-letter queue with a named owner.

Trial checklist

Identity batch: 10 contacts Clio to HubSpot, 10 HubSpot to Clio. Zero duplicates created. Email and phone both matched on the second pass.
Custom field batch: multi-select and enum values survive the iterator and aggregator. Unmapped values land in the fallback store, not in the void.
Matter to deal batch: matter type resolves to the right dealstage. Open-deal search stops a second deal on the same contact.
Status change batch: a milestone in Clio pushes a note to HubSpot within the agreed window. No echo back to Clio.
Attribution batch: utm_source and campaign fields written once from HubSpot, never overwritten by a Clio event.
Failure drill: force one 429 and one bad enum. Both land in the failure log with a replay path you can execute.
Rate limiter proof: a 50-record burst stays under the 100 requests per minute Clio ceiling with the token bucket in front.
Replay drill: replay one event with its original idempotency key. Confirm zero new records and a marked log entry.
Privilege check: billing, time entries and privileged notes stayed in Clio. Nothing sensitive crossed to HubSpot.

Section 6 · FAQ

Does this work if we only use one direction?

Yes. The source-of-truth matrix is valid with a single direction. Start there if the team is not ready for bidirectional writes. The dedupe gate and the failure log matter either way.

What about custom fields unique to our firm?

They go in the dictionary like any other property: Clio field, HubSpot property, type, transform, fallback. Anything you cannot map lands in the fallback store with a daily report instead of vanishing.

How fast is the sync in practice?

Event-driven for single record changes. Bulk work runs through a queue in front of the Clio rate limit of 100 requests per minute. The blueprint covers both paths.

Will this prevent every duplicate?

It prevents the ones the dedupe gate can see: email, phone, domain, external id, plus idempotent replays. Duplicates that already exist need a merge pass first. That is the repair kit, not the sync map.

What must never sync?

Billing, time entries and privileged notes stay in Clio. They do not belong in a CRM, and moving them creates compliance exposure with no business benefit.

Yes. The blueprint stands alone. The same field dictionary, dedupe gate and replay log ship as a client engagement through CRM and API workflow overhaul.

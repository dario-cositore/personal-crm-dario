This is the repair kit for the layer between your forms, your CRM and your follow-up. Duplicate records, blind creates, owner assignment nobody can explain, no timer when a lead ages. The rebuild I ran for Meridian Legal Group started there: three office locations, twelve intake channels, a HubSpot data graveyard, duplicate contacts in the thousands and no SLA timers at all. The same rules below are the ones I left running.

Before you start

Most duplicate problems come from lazy creation logic. Create contact. Create deal. Send alert. Move on. Fast build, dirty future. A serious layer works in the opposite order. Capture the event. Normalize identifiers. Search existing records. Score possible matches. Update the right record. Create only when safe. Associate the right company, deal, note and owner. Store the source event. Log the decision.

Ground rules: take the inventory before you change anything. Find every path that can create a contact, a company or a deal. Forms, ad leads, calendar bookings, payment events, imports, old Zapier and Make flows, partner feeds. Then stop the sources before you clean the pile. Cleanup without stopping the source is a treadmill.

Section 1 · Where duplicates enter, and how to stop them

Duplicates are not random. They enter through specific paths and each path has a specific fix. Name the path, then close it.

Identity normalization

Do not search raw form data. Raw form data lies. Email can include spaces and casing differences. Phone can arrive in five formats. Domain can include protocol, paths, subdomains and tracking junk. Normalize first, store both values.

email_normalized    = lower(trim(email))
phone_normalized    = e164(phone)
domain_normalized   = root_domain(url)      # strip protocol, www, path, utm
source_record_id    = provider + ":" + record_id
external_customer_id = stripe_customer_id | platform_customer_id
name_key            = lower(replace(full_name, " ", "_"))

raw values  -> stored as evidence, never used for matching
normalized  -> drives matching and idempotency

Search-before-create

This rule pays for itself immediately. Before creating a contact, search by normalized email. If no match, search by normalized phone. If no match, search by known external IDs. If no match, search by company domain with the person name as a candidate only. Then decide.

OrderMatch typeConfidenceActionNotes
0idempotency_key1.00Return previous result if processedReplay safety
1exact_email1.00Update existing contactPrimary key
2exact_phone0.92Update if no conflictE.164 form
3external_id1.00Update existing contactStripe, Calendly, Typeform
4company_domain + name0.74Manual review candidateNever auto-merge
5fuzzy name + company0.55Watch flag, new recordLow confidence

Exact matches can update automatically. Ambiguous matches go to review. No match creates a new record. That is the whole decision tree, and it is what stops blind creation.

Idempotency keys

Webhooks retry. Forms resubmit. Payment tools replay. CRMs fire update events after creation. Build a key from stable event data and store it.

{
  "event_type": "lead.submitted",
  "source_system": "typeform",
  "source_record_id": "tf_resp_01HYY4K8Q2",
  "idempotency_key": "contact_dedupe:typeform:tf_resp_01HYY4K8Q2:ops@example.com",
  "correlation_id": "corr_dedupe_01HYY4K8Q2",
  "received_at": "2026-04-26T21:08:19.219Z",
  "raw_payload_stored": true
}

If the key already succeeded, return the previous CRM object ID. Do not write again. This single rule removes the easiest class of duplicates: the second copy created by a retry storm.

Deals and ownership

Before creating a deal, search for open deals on the contact or company in the same pipeline. If one exists, update its context instead of opening another.
Preserve the existing owner on update unless a higher-priority routing rule overrides it. Owner churn is how follow-up history becomes unreadable.
Attach the source event as a note on the surviving record. The record should answer where it came from without opening a log.
Score leads only after identity resolves. Three contacts for one buyer means three partial scores and a wrong route.
Contact dedupe alone does not clean the pipeline. Duplicate deals are worse than duplicate contacts because they poison pipeline value directly. Search open deals before creating opportunities, every time.

Section 2 · Merge rules and conflict resolution

Automation should not merge records from weak evidence. Merge only from strong evidence. Medium confidence waits. Low confidence creates a new record with a watch flag. That gives you speed without a merge that destroys context.

Merge decision bands

BandConfidenceEvidence requiredAction
Auto merge0.90 to 1.00Exact email, exact external ID, or phone plus matching nameUpdate survivor, archive loser, write merge log
Review0.55 to 0.89Domain plus name, same phone different name, similar name same companyOpen candidate task, hold writes
Watchbelow 0.55Weak signal onlyCreate new record with watch flag, no merge

The review band is the one you tune. Move the lower bound up when reviewers keep rejecting auto-suggested merges. Move it down only when you can show the reviewer queue is reading correct suggestions.

Section 3 · Routing reasons your sales team can read

Assignment is useless if nobody can explain it. Every record carries a routing reason written at the moment of assignment. Not a score. A sentence a rep can read on Monday morning.

Routing reason format

routing_reason = {
  "decision_id": "rt_01J2K9M4",
  "decided_at": "2026-04-27T10:02:01.004Z",
  "channel": "typeform_intake",
  "matched_rules": [
    {"rule": "practice_area_fit", "value": "employment",
     "weight": 0.45, "source": "form.field.case_type"},
    {"rule": "urgency_signal", "value": "high",
     "weight": 0.30, "source": "form.field.deadline"},
    {"rule": "office_proximity", "value": "office_north",
     "weight": 0.25, "source": "geo.normalized_postcode"}
  ],
  "assigned_to": "user_42",
  "assigned_office": "office_north",
  "tie_break": null,
  "readable": "Assigned to M. Rossi (Office North): employment fit, high urgency, postcode nearest Office North.",
  "correlation_id": "corr_route_01J2K9M4"
}

The readable string is not decoration. It is what stops the managing partner from reassigning leads by hand every morning because nobody trusts the black box.

Every assignment writes routing_reason, decision_id and correlation_id on the record before the notification fires.
Inactive owner IDs are rejected at the routing layer, not after the lead has sat in a dead inbox.
Manual reassignment keeps the original reason and appends a second reason. History does not get rewritten.
If no rule matches, the record goes to a named queue with reason "no_rule_matched". It does not sit unowned.

Section 4 · SLA timers and the escalation ladder

Before the rebuild, Meridian Legal Group had no SLA timers at all. Leads aged quietly. Partners found out on the weekly report. A timer is not a notification. It is state attached to the record that escalates on its own when nobody acts.

Timer rules

Timer state lives with the record, not with the workflow run. A scenario restart must not reset the clock.
Business hours only for client-facing escalation, configurable per lane. After-hours clocks do not page people for a form fill at 23:40.
First response is measured against the assigned owner, not the queue. Owning a lead starts the clock.
Reassignment restarts the response window for the new owner and writes a second reason. The original breach stays recorded.
Every escalation writes an immutable event. You can reconstruct who was asked to act and when.

Three step escalation ladder

Three steps. Each step names who gets asked, what channel, and what happens if the step expires. The Meridian rebuild used the two hour and four hour steps below as its enforcement points.

Retry, backoff and dead letter

Workflows fail. The question is where the failure lands. Every write path needs the same three answers: how it retries, how it backs off, and where it goes when retries are exhausted.

FailurePolicyBackoffAfter max attempts
CRM search rate limitedRetry with backoffExponential with jitterDead letter queue
Multiple exact matchesManual review, no retryNoneReview queue
Missing email and phoneManual review, no retryNoneReview queue
API auth failureAlert operator, stop writesNoneOperator queue
Transient 5xxRetryExponential with jitterDead letter queue
Schema validation failOne corrected retryImmediateDead letter queue
Max attempts set and stored on the event. Five is a sane ceiling for CRM writes. Cap it, do not hope.
Exponential backoff with jitter, not a tight retry loop. A tight loop against a 429 is how you earn a longer ban.
Dead letter queue named and owned. crm_dedupe_failed_events in the sample payload below. Every item keeps its raw payload and correlation ID.
Dead letter items are reviewed on a schedule. Replay, fix, or drop is a decision. Silence is not.
"failure_policy": {
  "crm_search_rate_limited": "retry_with_backoff",

Section 6 · FAQ

Do I need to replace my CRM?

No. The layer sits between your sources and the CRM you already pay for. HubSpot, Salesforce, GoHighLevel, Clio, MyCase. The rules change with the API, not with the logo.

What if I already have thousands of duplicates?

Stop the sources first. Then clean in batches, starting with records tied to active pipeline. High-value contacts next, recent leads next. Records with conflicting owners, conflicting email or phone, or payment history go to review. Protect revenue history before vanity cleanliness.

Why not just auto-merge everything that looks close?

Because a bad merge destroys context you cannot rebuild. Attribution splits, ownership confuses, payment history goes missing. Merge only from strong evidence. Review the middle band. That is the whole policy.

What exactly is a routing reason?

A structured object and a readable sentence written onto the record at assignment time. Which rules matched, what they weighed, who was assigned, and what the tie break did. Sales can read it without asking ops.

How long before the SLA ladder matters?

Immediately if you have leads ageing without anyone noticing. The Meridian rebuild went from no timers at all to enforced first response with three steps. The timers are what made the rest of the rebuild visible.

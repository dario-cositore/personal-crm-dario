Every form fill, ad conversion and chat message goes through the same seven stages: validation, dedupe, enrichment, scoring, routing and assignment. This pack is the buildable version of that pipeline. Stage by stage, with the keys you set and the way each stage fails.

The pipeline

One unified webhook endpoint accepts form fills, chat transcripts and ad conversions. Payloads get normalized and schema-checked before anything else happens. From there the lead moves left to right, then writes back and notifies.

ingress | v [01 Capture] -> [02 Validation] -> [03 Dedupe] -> [04 Enrich] -> [05 Scoring] | v [07 Assign] <- [06 Router] <- -----------------------------------+ | ^ | +---- conflict resolver (score or territory tie) v [CRM write] -> [Notifier: Slack / SMS / Email] -> [Dashboard readback] dead-letter queue + correlation log on every hop

Stage-by-stage build guide

01Capture gateway

Inputs: website and landing page forms, webinar and content downloads, Facebook Lead Ads, Google Ads conversions, LinkedIn Lead Gen Forms, Drift or Intercom chat transcripts.

Config: one public endpoint. Normalize every source into your internal event contract before anything downstream reads it. Preserve event_id, correlation_id, idempotency_key, source_system, source_record_id, utm_source, utm_campaign. Store the raw payload alongside the normalized one.

Guardrail: HMAC signature verification on the endpoint before processing. Unauthorized test submissions are a real source of junk records.

Failure behaviour: non-2xx to the provider, payload persisted for replay, alert if the error rate moves. Budget 150 ms.

02Validation

Inputs: the normalized event.

Config: schema and sanity checks. Required fields present. Email format valid. Consent captured where regulation needs it. Enum fields limited to allowed values. Budget and urgency checked against the list you actually route on. Session and UTM context passes through untouched.

Rule: reject to a review queue, do not write a partial record. A contact created with an empty required field is worse than no contact, because the follow-up sequence will fire on stale data.

Failure behaviour: reject count and reasons logged per field, dead-letter queue holds the payload. Budget 100 ms.

03Dedupe (Redis + fuzzy)

Inputs: validated event.

Config: deterministic match on email and phone. Fuzzy match on company name and normalized domain. Redis keyed on normalized values for the lookup, target under 100 ms. Merge strategy per field: first non-empty wins for contact fields, latest wins for behavioural fields, never overwrite a human correction.

Order of operations: search contact by email, search company by domain, search open deals by contact and pipeline, update when found, create only after the search clears. Store every object ID against the original event.

Failure behaviour: ties and near-matches go to the conflict resolver, never auto-merged. Every merge logged with its inputs. Budget 100 ms.

04Enrichment

Inputs: deduped identity (email, domain, company name).

Config: parallel lookups against providers such as Clearbit and Apollo, plus LinkedIn where your licence allows it. Cache keyed on domain with a TTL you can defend. Warm the cache on your top 200 domains before cutover.

Rule: a lead never waits on a lookup. Hard timeout per provider, then fall through to cached data and mark the record enrichment: partial.

Failure behaviour: circuit breaker per provider, staggered re-enable, alert when the cache hit rate falls below your floor. Budget 3000 ms including timeout.

05Scoring

Inputs: firmographic fit, behavioural interest, source, campaign, prior interaction history.

Config: one 0 to 100 score. Keep the inputs visible on the record: fit component, behaviour component, and the rules that fired. Retrain on conversion outcomes so routing decisions improve as the dataset grows.

Rule: if a model classifies messy text, force it to choose from a closed list and validate the choice: sales_priority, sales_standard, founder_review, nurture, reject_spam, manual_review_missing_data. Store the raw answer beside the summary. Raw pain tells you what the buyer said. Summaries compress, and compression loses edge.

Failure behaviour: score outside 0 to 100 or missing inputs routes to manual_review_missing_data. Budget 400 ms.

06Router

Inputs: score, territory, availability, existing owner, open deal status, customer status.

Config: territory rules by region, account book, segment or language. Load balancing across active reps. Account-based routing, round-robin and skill-based assignment run through the same engine so there is one place to inspect.

Rule: owner status is checked at routing time, not trusted from the record. An inactive owner ID is the fastest way to lose a lead. Log the decision: which rule, which evidence, which rep.

Failure behaviour: unresolved territory or tie goes to the conflict resolver, then to a manual queue with an SLA timer. The router keeps a dead-letter queue for anything it cannot place. Budget 250 ms.

07Assign and notify

Inputs: resolved owner, lead record, context note.

Config: write to CRM, then fire the notification hub: Slack, SMS, push and email with priority queuing. Include enough context in the alert that the rep does not open the CRM to decide whether to care.

SLA escalation: if the primary rep does not acknowledge inside the window, escalate to the next rep automatically, then to the team channel. Timer state lives with the lead so a restart does not lose it.

Failure behaviour: notification failure does not roll back the assignment, it pages. Budget 300 ms assign, 400 ms notify.

Make.com scenario outline

Plain module sequence. This is the shape, not a replacement for the config above. Put error handlers on every module that writes.

1  Webhook (custom trigger)          receives raw payload
2  HTTP: verify HMAC signature       reject unsigned calls
3  Tools: set variable               event_id, correlation_id, received_at
4  JSON: parse + schema validate     required fields, types, enums
5  Router A: valid / invalid
   5a  Data store: append rejected   dead-letter record with reason
   5b  Router B: match or new
6  Search: CRM contact by email
7  Search: CRM company by domain
8  Search: CRM open deals by contact
9  HTTP: Redis GET normalized key    deterministic dedupe hit
10 HTTP: fuzzy score company/domain  near match under threshold
11 Router C: create / update / conflict
   11a HTTP: Clearbit enrich          parallel, hard timeout
   11b HTTP: Apollo enrich            parallel, hard timeout
   11c Tools: merge cached fallback
   11d HTTP: scoring service          0 to 100 + routing label
   11e Router D: territory + load + owner status
   11f HTTP: conflict resolver        ties and high-value leads
12 HTTP: CRM create or update        idempotency key header
13 HTTP: CRM associate objects        contact, company, deal, note
14 Data store: append audit row       before, after, rule, owner
15 Slack: priority alert to rep
16 SMS / email: fallback channel
17 Error handler (attached to 4,9,11a,11b,11d,12,15)
   -> HTTP: alert on-call
   -> Data store: append failure with correlation_id
   -> route to DLQ for replay
Rate limits: put a token bucket in front of the CRM. Bulk operations against a 100 requests per minute ceiling will throw 429s the moment you go live with real volume. Concurrency with exponential backoff and jitter, not a retry loop.

Latency budget

Measured per stage rather than guessed at the end. Each stage gets a hard ceiling. If a stage blows its ceiling, that is the alert, not a later complaint about slow leads.

Headroom to the ceiling is deliberate. It absorbs one retry cycle and a cold enrichment cache without failing the promise.

Weekly review checklist

Every dead-letter item from the week has an owner and a decision: replay, fix, or drop.
Duplicate merges reviewed, each one logged with its inputs.
Escalations counted, with the rule that fired each time.
Scoring model inputs still match the fields you actually capture.
Owner roster checked against active users in the CRM.
Latency budget reviewed per stage, not as a single end number.

Build order if you cannot do it all at once

  1. Capture and validation. One endpoint, one contract, rejects visible.
  2. Dedupe. Search before create beats every downstream cleanup.
  3. Assignment and notification. Even a crude router beats no router.
  4. Failure path. Dead-letter queue, correlation log, alerts that page.
  5. Enrichment and scoring. Add once the boring layers are trusted.
Why that order: the stages above the write path protect the record. Enrichment and scoring make the record smarter, they do not make it correct. Fix correctness first.

FAQ

Does this replace the systems blueprint?

No. The blueprint explains the architecture. This pack is the build version: keys, module order, payloads, budgets and thresholds.

Which orchestration tools does it assume?

Make.com for the outline, since it handles nested iterators and error handling well. Zapier, n8n and custom API receivers map to the same stage boundaries.

What if my volume is small right now?

Keep the same stage boundaries. Shrink the budgets, keep the dead-letter queue. Volume changes the sizing, not the shape.

Where does AI actually fit?

Classifying messy pain text, urgency and fit in scoring, with a closed list of allowed outputs and validation on the choice. The final routing path still gets a strict schema.

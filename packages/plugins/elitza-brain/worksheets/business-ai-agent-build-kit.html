An agent your team cannot audit is an agent your team cannot own. This kit is the skeleton I put under every client build: a role card with hard edges, a tool registry with permission levels, a memory schema with deletion rules, recovery routes for when a model or an API misbehaves, and a monitoring plan for the first two weeks. You get the worksheets, the schemas and the checklists.

Before you start

Most agent problems are not model problems. They are boundary problems. The agent was never told what it may do, what it may touch, what it may remember, or who it wakes up when it is wrong. Fix the skeleton first. The prompts get easier once the edges are real.

Ground rules: write the role card before any tool is wired. Register the tool before it is called. Decide retention before the first write to memory. Define the recovery route before go-live, not after the first silent failure. One agent, one job, one owner.

Section 1 · Role card: what the agent may and may not do

The role card is the job description with teeth. It names the job, the systems, the verbs the agent may execute, the verbs it may only propose, and the things it never does. If it is not on the card, the agent does not do it.

Boundary tests for the role card

One sentence job: if the job needs an "and" to cover a second domain, you are describing two agents.
May execute is a closed list: every verb maps to a tool in the registry. No open verbs.
May only propose covers anything client facing: the agent drafts, a human clears the gate.
Never does is explicit: deletes, permission changes, schema changes and external sends sit here by default.
Escalation has triggers: low confidence, missing field, tool error, blocked action. "If unsure" is not a trigger.
Worked shape: in the Nexus SaaS onboarding build the agent owns the first 72 hours of customer onboarding: create workspace, import data, configure integrations, walk the first three actions via in-app messages, schedule training and send a setup summary. Humans keep the 20 percent that needs judgment, like complex migrations and custom integrations. Same pattern every time. Narrow job, hard edges, named human for the rest.
Common role failure: giving the agent a persona and hoping a persona is a boundary. Tone does not constrain action. Only the may-execute list and the tool permissions do.

Registry checks

Every may-execute verb has a registry row. Cross-check Table 1A against Table 2A until both are empty of surprises.
Level matches the blast radius. Client-facing sends sit at L2 or L3. Internal field writes sit at L4. Admin stays out.
Fields are allowlisted on writes. A scoped token without a field list is not scoped.
Each tool has an on_error route: dead-letter, manual queue, or log-and-continue, chosen deliberately.
Model tools use closed label lists and store the raw answer beside the summary. Compression loses edge.
Approval gates for anything client facing: if a human outside the company can read it, the write is L2 or L3. The agent may draft the email, the post or the reply. A named approver clears the gate. That is the difference between an assistant and an intern with the send button.

Audit checks for memory

Every memory write records its source: event id or document id, timestamp, and which tool wrote it.
Session state is short lived. Long retention on ephemeral state is how stale context leaks into new runs.
Personal data has a deletion path that runs without a developer, on request.
Vector stores have a rebuild path from the source of truth. Embeddings without a source document become unverifiable memory.
Logs are append only with their own retention. Memory and logs expire on different clocks on purpose.
Common memory failure: treating every conversation as permanent context. The agent recalls a discount promise from four months ago and acts on it. If the memory schema cannot show when a fact was written and from what event, it cannot be trusted at decision time.

Section 4 · Failure recovery and alerting

Models miss. APIs throttle. Tokens expire. The skeleton is finished when every one of those has a route: what the agent does next, what gets stored, and who gets told. Recovery is a designed path, not a retry flag.

Table 4A · Failure recovery routes

FailureLayerAgent behaviourWhere it landsAlert rule
Example: model returns off-list labelmodelreject, ask humanmanual_review queueimmediate if rate above 5%
HubSpot 429 rate limitAPIbackoff, queue, retryretry queuealert if retry age over 15m

Alert rules worth writing down

Auth failures page immediately. A 401 or 403 means a key rotated or a scope narrowed. The workflow will keep running blind otherwise.
Model reject rate has a threshold: sudden drift after a provider change shows up as rejects, not as bad output you happen to notice.
Queue age alerts: items older than the threshold, not just queue length. Length hides stuck items behind healthy ones.
Silent success is a failure signal: zero runs in a window when runs are expected means the trigger died.
Blocked actions alert the owner: when the agent correctly refuses, someone should see that the refusal happened.

Recovery contract

{
  "failure_id": "model_off_list_label",
  "detect": "label not in closed_labels",
  "agent_behaviour": "reject_decision",
  "preserve": ["raw_model_output", "input_fields", "event_id"],
  "route_to": "manual_review_queue",
  "retry": false,
  "alert": {
    "channel": "#ops-agent-alerts",
    "when": "any occurrence",
    "include": ["event_id", "label_raw", "agent_id"]
  },
  "human_action": "relabel or split case, then close the queue item"
}
What recovery is for: the next break should announce itself. If a failure can happen twice before anyone hears about it, the route is not finished. Every item in Table 4A needs a queue, a payload and a name.

Section 5 · Handover: monitoring the first two weeks

The first two weeks decide whether the agent becomes infrastructure or a demo. Run the same checklist every day. The numbers do not need to be perfect. They need to be visible to the person who owns the role card.

DAYS 1-3Daily read of the raw path

What I check: every run end to end against real inputs, raw payloads and raw model output on screen.

Evidence: run log, decision log, one blocked action if one occurred.

Pass condition: no silent drops, no unexplained writes, every reject has a queue item.

Common failure: reviewing only the summary dashboard. The dashboard is the last place a bug shows up.

DAYS 4-7Gate and permission review

What I check: who cleared which gate, what was auto-executed, any token errors.

Evidence: approval records, 401/403 log lines, field-write audit.

Pass condition: every L3 write has a decision record, every L4 write is inside the allowlist.

Common failure: approver rubber-stamping. If the review screen shows nothing useful, fix the screen.

DAYS 8-12Memory and retention check

What I check: what memory the agent used in its last 20 decisions, and whether each fact has a source.

Evidence: memory read log, written_at and source_event_id on stored facts.

Pass condition: no decision rests on a fact with no source, no stale session state past retention.

Common failure: memory growth with no purge job. Retention without a deletion method is a comment.

DAYS 13-14Ownership transfer

What I check: the client owner runs the review without me, clears one gate, answers one alert.

Evidence: signed checklist, token register with owners, runbook page for the alert they handled.

Pass condition: the role card owner can explain the last failure and the recovery route.

Common failure: handing over dashboards instead of decisions. Ownership is who decides, not who watches.

Section 6 · FAQ

Is this a prompt pack?

No. Prompts sit inside a role card, a tool registry and a recovery route. This kit is the skeleton those prompts run in. The prompts are the easy part once the boundaries are real.

What stacks does it cover?

HubSpot, Salesforce, GoHighLevel, Zendesk, Jira, Slack, Make.com, Zapier, n8n, document stores, webhooks and custom APIs, with Claude API or another model endpoint for classification and drafting. If the agent can call it, it goes in the registry.

Do I need an engineer to fill this in?

You need someone who knows the systems and the fields. The worksheets are written for operators. The JSON schemas are there so an engineer can lift the contracts without translating them.

How does this relate to the Spec Pack?

The Spec Pack fixes scope, gates, data path and price before a build starts. This kit is the agent structure you build once the scope is agreed. Spec first, skeleton second.

Can I use it for more than one agent?

Yes. One kit per agent. The point of the skeleton is that the second agent is a second role card and a second registry, not a rewrite of your standards.

What if I want it built instead of filled in?

That is a Business AI Agents engagement. You can also take the completed worksheets to your own team. The format does not depend on who builds it.
